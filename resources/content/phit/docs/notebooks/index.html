Each implemented estimator should have an executable notebook walking through its objective, solution, residuals, uncertainty, likelihood (where relevant), and numerical edge cases. Start with OLS; do not create placeholder notebooks for methods the project does not implement.

  • OLS mathematics: derives the estimator and evaluates each intermediate quantity on the PHP example data.
  • OLS verification: estimates identical models in R, Python statsmodels and the PHP extension, displays results and checks agreement.

The walkthroughs are authored as Quarto .qmd files. The rendered website includes saved outputs from docs/_freeze/ so readers can follow the calculations without running them. Executable Python chunks show intermediate matrices and invoke R/PHP through subprocesses for comparisons. The production library still requires neither Python nor R.

Writing future walkthroughs

Use a small reproducible simulated dataset with named variables, units, noise, and meaningful relationships. State its generating equation, seed, population parameters, and observed sample correlations. Save and share the actual observations; label them synthetic and explain that correlation alone is not causation. See the learning-data convention. State the model assumptions and input ordering, derive the calculations before displaying them, connect fields to production code, and explain edge cases. Supply equivalent R, statsmodels and PHP calls when those references support the estimator. State any differences in statistical conventions rather than silently adapting one library’s results. Keep assertions near the results and preserve executed outputs. Share inputs with reference tests where possible; avoid three separate datasets that only look similar.
