phit provides statistical models and numerical routines through PHP functions with explicit inputs and array results. Numerical behavior is checked against reference implementations on shared inputs.

Principles

  • Plain inputs and outputs. Functions take PHP arrays, or a table object with toModelData() or toColumns(), and return associative arrays. There are no model objects or services.
  • Two levels of input. The formula functions build a design from named columns as R does. The *_matrix functions take a literal design for code that builds its own. Both call the same estimators.
  • Documented defaults. OLS inference is homoskedastic with 95% t intervals. Logistic, probit, and Poisson fits use maximum likelihood with 95% normal Wald intervals. Rank-deficient designs are rejected, and undefined statistics are NAN or INF.
  • Visible missing-data handling. Incomplete rows are dropped with a warning and reported in every result, or rejected with missing: 'raise'. See Missing values.
  • Evidence for each estimator. Each estimator has a mathematical walkthrough and a comparison with R, lme4, or statsmodels where they support it. Agreement is claimed only for the tested cases.
  • Simple implementation. Each model has a dedicated estimator. phit has no general GLM framework and no generic Model, Family, Link, or Optimizer traits for hypothetical future models.

Architecture

Component Responsibility
stats-core Estimation, inference, and numerical validation. It takes Rust vectors and returns a dedicated result struct or a StatsError, with no PHP types.
php-extension PHP value inspection, formula parsing and design construction, numeric conversion, missing-row filtering with warnings and accounting, exceptions, result arrays, and the CSV reader.
Rust crates Matrix decompositions, special functions, and optimizers. phit’s own code expresses the statistical formulas.

phit uses Rust-native numerical crates. An external BLAS or LAPACK backend needs a demonstrated numerical, performance, or deployment benefit and must preserve the contract and reference agreement. An Apple Accelerate experiment showed no speed advantage on the measured workloads and was removed.

Scope

phit fits OLS, binomial logistic and probit regression, Poisson regression, Gaussian mixed models by ML or REML with random intercepts and slopes, and a binomial logistic model with one random intercept by Laplace or adaptive quadrature. It also provides probability distributions, descriptive statistics, seeded sampling, posterior-draw kernels, and a CSV reader. The R compatibility ledger lists what is supported, what differs, and what is not supported.

The posterior-draw functions are numerical kernels for CmdStanPHP’s moment matching: weighted moments, covariance maps, and affine transforms. They use literal row and parameter order, never insert an intercept, and never drop rows. Stan evaluation, PSIS, iteration control, and diagnostics belong to the consuming package. See Posterior draws.

Before a feature is added, decide whether it changes estimation or only prepares data:

  • Data preparation belongs in packages such as phibble and phpolars, or in application code.
  • A numerical feature needs a concrete use case, an explicit contract, and verification before it enters the engine.
  • A new dependency or abstraction must solve a demonstrated problem.

Data preparation

phit reads CSV files and builds designs from formulas. Other preparation, such as selecting records, converting text under an explicit policy, or attaching labels, belongs to the caller or to table packages. Preparation code should make its choices visible: column order, intercept insertion, missing-value handling, and row alignment. It should preserve phit’s result or document any transformation, such as replacing nonfinite values for JSON.

Conventions for documentation and evidence

These conventions apply to contributors writing walkthroughs, verifications, and benchmarks.

  • Teaching data. Main examples use reproducible simulations with named variables, units, plausible ranges, and noise. Pages label the data as simulated, state the generating equation and seed, and save the observations so that Rust, PHP, R, and statsmodels fit the same sample. They report observed correlations rather than the intended relationship.
  • Walkthroughs. They distinguish observed inputs, constructed columns such as the intercept, generating parameters, trial values, and estimates. Matrix dimensions and intermediate values appear beside the steps. Small samples keep matrices readable, and their statistical limits are stated.
  • Shared samples. docs/data/housing.csv comes from tests/generate-learning-data.R, and docs/data/learning.csv from tests/generate-logistic-fixtures.R.
  • Benchmarks. Each estimator with reference support has an API-level benchmark against R and statsmodels. Numerical agreement on identical inputs is checked before timings are published. Reports record versions, machine, threads, raw measurements, and timing boundaries, and separate fitting from startup. Benchmarks are development commands, not unit tests.
  • Mixed models. Gaussian mixed models keep the marginal likelihood, variance components, and conditional group estimates visible in the code. BOBYQA and Nelder–Mead come from pinned Rust crates. The NLopt and PORT backends that lme4 can use are not available.
  • Approximate likelihoods. For non-Gaussian mixed models, pages separate agreement with R from integration accuracy. They state the approximation, compare like methods, and check node-count sensitivity with an independent integrator.
