The native library installs into PHP itself. Applications call fit_ols(), fit_poisson() and the other functions directly after the extension is enabled. The deployed PHP process does not need Cargo, R or Python. Build tools and the installer live in the build environment.

Names and supported packaging targets

  • Package: phpstats/phit (PIE/Packagist metadata).
  • Registered extension: phit; check extension_loaded('phit').
  • Installed module: phit.so, including the macOS phpize install path.
  • Direct Cargo output remains libphit.so on Linux and libphit.dylib on macOS. They contain the same native extension, using different filenames.

The registered extension name is phit: use it with extension_loaded(), get_extension_funcs(), phpversion() and Composer (ext-phit). Functions are in the Phit namespace (Phit\fit_lm, Phit\dist_normal_cdf).

Package metadata targets PHP 8.3, 8.4 and 8.5, non-thread-safe PHP, Linux and macOS. Windows and ZTS are excluded. Container and binary builds use Debian Bookworm/glibc. Alpine/musl and older glibc builds are not covered by these binaries. The CI matrix targets Linux amd64 at all three PHP versions. Actual local evidence and its architecture/version are recorded separately in the verification section; a configured CI job is not a passed job.

Build a ready-to-use PHP-FPM image

From the repository root:

docker build --target checks -f docker/Dockerfile -t phit:checks .
docker build -f docker/Dockerfile -t phit:local .
./scripts/check-container phit:local phit:checks

The build installs the extension through PIE 1.5.0 and runs the Rust/PHP gate. The isolated FPM check sends a real FastCGI request. The production-image check then exercises both CLI and FPM using the shipped PHP configuration and verifies identical OLS coefficients and a Poisson log-exposure fit.

The final image contains the PHP runtime and installed extension. Rust, Clang, PIE, Python, repository sources, and test utilities remain in the build stages. The image retains the official PHP entrypoint and foreground PHP-FPM command. Use it as an application base:

FROM phit:local
COPY app/ /var/www/html/

Connect your normal web server to FPM. FPM speaks FastCGI, not HTTP; no public FPM listener is needed for the tests. The verification script removes only its own temporary container and never edits a production PHP/FPM configuration.

Build pins and reproducibility

The Dockerfile pins PHP and Rust base images by OCI digest. The workflow records separate PHP 8.3/8.4/8.5 image digests. Build and runtime stages share exactly the same PHP image. Cargo.lock pins Rust dependencies; the downloaded PIE PHAR has a pinned SHA-256. Update those pins deliberately and rerun the gate.

Debian APT packages are resolved at build time. These pins establish a repeatable base and dependency selection, not a promise that every future rebuild has the same bytes. Binary manifests record the compiler, PHP API, architecture, libc, linked libraries, extension hash and Cargo.lock hash. This is preferable to claiming reproducibility without recording the environment.

Install through PIE

The package has not been submitted to Packagist or publicly released yet. Today, use a local checkout with PHP headers, phpize/autoconf/make, a stable Rust toolchain and libclang configured as in development.

To build without enabling or changing your PHP configuration:

pie repository:add --with-php-config=/path/to/php-config path "$PWD"
pie build 'phpstats/phit:*@dev' \
  --with-php-config=/path/to/php-config \
  --with-phpize-path=/path/to/phpize

To install that checkout, change build to install. PIE tries to enable the extension for the selected PHP installation. CLI and FPM can read different INI files: verify the application SAPI separately and restart its workers after installation. Source installation requires Rust/Clang; they are not runtime requirements. Pin a release version once published.

After Packagist registration and a tagged release, the public command will be:

pie install phpstats/phit:0.1.0

That public package command is a release target, not an available registry entry. The official PIE documentation explains installer selection, repositories, and PHP configuration.

Manual source installation and staging

The maintained pie/config.m4 and pie/Makefile.frag delegate the standard Unix PHP build to locked Cargo compilation:

cd pie
/path/to/phpize
./configure --with-php-config=/path/to/php-config
make -j4
# Stage without modifying the installed PHP runtime:
make install INSTALL_ROOT=/absolute/path/to/staging
# Or install after reviewing the build:
# sudo make install

Build as an unprivileged user before installing. The install goal requires the already built module and does not rerun Cargo under sudo. INSTALL_ROOT stages under the configured extension directory. On macOS, use the matching LLVM/header setup in the development guide.

Add extension=phit.so to the relevant PHP INI configuration after a manual install. Inspect php --ini for CLI; check the FPM configuration separately. Verify the native functions through both. Rebuild for another PHP ABI, architecture, thread-safety/debug configuration, or platform.

Binary artifacts

Create the tested Linux binary bundle locally:

docker build --target binaries --output type=local,dest=.context/binaries \
  -f docker/Dockerfile .

The archive name includes the library version, PHP major/minor, architecture, NTS mode and Bookworm target. It contains phit.so, installation instructions, a manifest, the project MIT license and dependency notices. A separate SHA-256 file checks archive integrity. Dependency notices include the Cargo dependency closure and build dependencies; exact upstream MIT notices missing from published crate archives are preserved under third-party/ with provenance hashes.

Treat a binary as matching the manifest’s build environment. It is not a universal Linux file. Verify its checksum, use the matching PHP extension directory, enable it for the required SAPIs, restart workers and execute a real fit.

Versioned release process

The installer/FPM workflow tests the supported Linux PHP matrix and prepares binary artifacts. The release workflow runs that matrix, checks tag/crate version agreement and MIT licensing, creates a source archive/checksum, then builds and tests installation from the extracted archive. Export rules remove generated website caches and figures while preserving the source, locked dependencies, model fixtures, test datasets and their original notices.

These workflows prepare GitHub Actions artifacts. They do not publish GitHub Releases, container images or Packagist entries. No release tag is created by a build or test command. Maintainer publication remains a separate deliberate step:

  1. Complete all numerical/API checks on the exact intended source revision.
  2. Check Linux CI and the documented platform/PHP support matrix.
  3. Review source/binary artifacts, checksums and notices.
  4. Align both Cargo versions; create the corresponding vX.Y.Z tag when authorized.
  5. Publish the approved release artifacts and register/update Packagist metadata.

Composer can declare "ext-phit": "*" as an application requirement. That checks availability; PIE or the deployment image installs the native extension. No userland Composer framework is needed.

Deployment verification

tests/deployment.php verifies extension identity/version, automatic-intercept OLS, and a closed-form Poisson log-exposure model. scripts/check-fpm sends an isolated FastCGI request; scripts/check-container checks the final runtime image using its normal FPM pool. The scripts compare CLI/FPM version, coefficients and fitted rate. They fail on a loader error or wrong output instead of trusting php -m.

The recorded packaging verification states which local image/version/architecture actually passed. Remote CI results and registry publication must be checked independently before announcing a release.
