Practical guidance

  • Polars memory is outside PHP’s memory manager, so memory_limit does not count it. PHP arrays built from a result do count.
  • rows() and iterRows() build PHP arrays for every row. On 200,000 rows of 22 strings, they use about 340 MB of PHP memory. Calling rows() on each slice from iterSlices(10000) keeps PHP’s peak near 20 MB.
  • Collecting 1M rows into PHP takes about 0.2 s for plain columns, plus about 0.5 s for each datetime column, because each value becomes a DateTimeImmutable object.
  • A PolarsTable gains the most when a pipeline reduces the data (summaries, filters, or joins followed by summaries) or chains several verbs before collecting.
  • Reading files with Phpolars\read_csv() or read_parquet() and wrapping the result with PolarsTable::fromPolars() avoids parsing the file in PHP.
  • A verb given a PHP closure converts a PolarsTable to a phibble DataFrame and back. That costs about 1 s per million rows with a datetime column. Use expressions on large data, or phibble’s in-memory DataFrame for closure-heavy pipelines.
  • For a filtered scan of a large file, collect(engine: 'streaming') keeps much less in memory. Memory on large files has the measurements.

phplyr pipelines on three backends (best of three)

bench/phplyr.php runs phplyr pipelines on phibble’s in-memory DataFrame, PolarsTable, and phibble’s SqlTable over SQLite. The data is a sales table (store, product, day, units with 2% NA and 5% zeros, price) and a 100-row store lookup. Loading is not timed. Each pipeline is timed through collect(), which builds a Phibble\DataFrame, and the results of all backends are compared.

  • A: filter, left join, grouped summary, then a ranked window within regions.
  • B: per-store windows over every row: lag(order_by: day), cumsum, and a share of the group sum.

Memory on large files

The query filters a 500 MB, 22-column CSV and keeps 4% of its rows (a 17 MB result). Measured on 2026-10-30 at 810f689.

Engine Peak footprint, macOS Anonymous memory at the end, Linux
default (in memory) about 550 MB 485 MB
streaming, 1 thread about 100 MB 80 MB
streaming, 4 threads about 130 MB 115 MB
  • The Linux numbers come from Docker with the dist build. tests/memory.php checks the bound on both systems.
  • scan_csv() applies filters in the reader with either engine. A filter that keeps no rows reads the same file in 45 to 100 MB of process memory.
  • With the default engine, kept rows cost more than their own size. A String column that keeps a few strings from a parsed batch holds the batch’s whole buffer. The streaming engine, added in v0.2.1, copies the kept strings into buffers of their own.
  • Polars maps the CSV file into memory, so a process’s resident set size also includes up to the file’s size in pages that the operating system can reclaim. The macOS footprint leaves these pages out.
  • The sink*() methods stream a result to a file without collecting it.
