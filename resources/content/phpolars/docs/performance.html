Practical guidance

  • Polars memory is outside PHP’s memory manager, so memory_limit does not count it. PHP arrays built from a result do count.
  • rows(), toDicts(), and iterRows() build PHP arrays for every row, which can take far more memory than the data does in Polars. Calling rows() on each slice from iterSlices(10000) keeps PHP’s peak low.
  • Collecting rows into PHP costs time in proportion to the rows and columns returned. Datetime columns cost the most, because each value becomes a DateTimeImmutable object.
  • A PolarsTable gains the most when a pipeline reduces the data (summaries, filters, or joins followed by summaries) or chains several verbs before collecting.
  • Reading files with Phpolars\read_csv() or read_parquet() and wrapping the result with PolarsTable::fromPolars() avoids parsing the file in PHP.
  • A verb given a PHP closure converts a PolarsTable to a phibble DataFrame and back. Use expressions on large data, or phibble’s in-memory DataFrame for closure-heavy pipelines.
  • For a filtered scan of a large file, collect(engine: 'streaming') runs in batches and keeps less in memory.

A CSV pipeline

bench/pipeline.php reads a 1M-row, 16 MB CSV, filters it, groups and aggregates it, and returns PHP arrays. bench/make-csv.php generates the CSV with a fixed seed: a string group column with 50 values, an integer column with about 2% missing values, and a float column. Each run is timed from read_csv() through toDicts(), so it includes parsing the file and building the PHP arrays. Each implementation runs in its own process, and all produce the same result.

Implementation Median Range of 7 runs Peak memory
phpolars, 1 thread 70 ms 67–73 ms 95 MiB
phpolars, 2 threads (default) 46 ms 45–49 ms 105 MiB
phpolars, 4 threads 53 ms 50–56 ms 145 MiB
plain PHP arrays (fgetcsv loop) 786 ms 785–787 ms 4 MiB

The machine has 2 cores, so 4 threads compete for them and run slower than 2. Plain PHP keeps only running totals, so its memory stays small.

phplyr pipelines on three backends

bench/phplyr.php runs phplyr pipelines on phibble’s in-memory DataFrame, PolarsTable, and phibble’s SqlTable over SQLite, with phibble v0.6.0 and phplyr at 42b2ae0. The data is a sales table (store, product, day, units with 2% NA and 5% zeros, price) and a 100-row store lookup. Loading is not timed. Each pipeline is timed through collect(), which builds a Phibble\DataFrame. All backends return the same result.

  • A: filter, left join, grouped summary, then a ranked window within regions.
  • B: per-store windows over every row: lag(orderBy: day), cumsum, and a share of the group sum.
  • C: pipeline A with a PHP closure in filter().

Memory on large files

  • scan_csv() applies filters in the reader with either engine, so rows that a filter rejects are not kept.
  • With the default engine, kept rows can cost more than their own size. A String column that keeps a few strings from a parsed batch holds the batch’s whole buffer. The streaming engine copies the kept strings into buffers of their own.
  • Polars maps the CSV file into memory, so a process’s resident set size also includes up to the file’s size in pages that the operating system can reclaim.
  • tests/memory.php checks that a filtered streaming scan holds much less than the file.
  • The sink*() methods stream a result to a file without collecting it.
