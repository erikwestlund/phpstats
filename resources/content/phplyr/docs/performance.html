phplyr’s functions call one or two methods of the table they are given, so the backend determines how fast a pipeline runs.

Choosing a backend

  • In-memory DataFrame suits data that fits in memory. Expression arguments such as mean('x') let phibble compute a grouped summary in one pass, without building a table per group as a closure does.
  • A database table (Phibble\tbl()) avoids loading the data into PHP. With expressions, filter() and summarise() run in the database, and only the result reaches PHP.
  • Pipelines that return every row (mutate(), arrange(), unfiltered joins) spend most of their database time transferring rows to PHP.
  • Closures on a database table load all rows first and then run in memory. Use col() expressions and phplyr’s helpers to keep the work in SQL.
  • SQLite columns need declared types. PDO binds values as strings. In an untyped column, SQLite stores them as text and compares numbers as text.
  • PolarsTable (phibble’s Polars backend, on the phpolars extension) runs expressions in Polars. A closure step converts the data to a DataFrame and back. PolarsTable::fromPolars(Phpolars\read_csv($path)) skips phibble’s CSV parse.

Benchmarks

Script Measures
bench/harness.php phibble’s shared workloads on DataFrame, SQLite, and PolarsTable, each as a phplyr pipeline and as direct table calls
bench/backends.php Three pipelines on DataFrame, PolarsTable, and SQLite, checking that all return the same rows
bench/backends.R Two of those pipelines with dplyr, checking row counts and column sums against phplyr’s
bench/models.php lm(), glm(), lmer(), and glmer() on the phit extension and phit-polyfill, one fresh process per run

Each reports the median of seven runs and lists every run. bench/generate.php writes the harness data with phibble’s generator and seed.
