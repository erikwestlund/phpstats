phplyr’s overhead

At 100,000 rows, the phplyr pipeline and the direct calls differed by at most 5% on every workload and backend, which is within run-to-run noise. Grouped slices, pivot_*(), and complete() build on the same table methods.

Choosing a backend

  • In-memory DataFrame suits data that fits in memory. In the grouped summary above, expression arguments took 0.13 s and closures 0.58 s, because phibble computes expressions in one pass without building a table per group.
  • A database table (Phibble\tbl()) avoids loading the data into PHP. With expressions, filter() and summarise() run in the database, and only the result reaches PHP. These timings exclude loading. Reading the 1M-row CSV into a DataFrame takes about 1.4 seconds.
  • Pipelines that return every row (mutate(), arrange(), unfiltered joins) spend most of their database time transferring rows to PHP.
  • Closures on a database table load all rows first and then run in memory. Use col() expressions and phplyr’s helpers to keep the work in SQL.
  • SQLite columns need declared types. PDO binds values as strings. In an untyped column, SQLite stores them as text and compares numbers as text.
  • PolarsTable (phibble’s Polars backend, on the phpolars extension) runs the pipeline in Polars and pays mainly for converting rows back to PHP. See below.

PolarsTable

bench/backends.php times three phplyr pipelines and checks that DataFrame, PolarsTable, and SQLite return the same rows. It is adapted from phpolars’ benchmark script. bench/backends.R runs pipelines A and B with dplyr and checks that its row counts and column sums match phplyr’s.

  • A: filter, join a store lookup, two-key summarise, then a ranking window.
  • B: grouped lag(orderBy:), cumsum(), and a share of the group total over all rows.
  • C: pipeline A with a closure in filter(). It has no dplyr version, because its closure is PHP code.

The full results, with every repeat and version, are in benchmarks/backends-results.json and benchmarks/dplyr-results.json.

Most of PolarsTable’s time goes to converting results to PHP values:

  • About 0.2 seconds per million rows of plain columns.
  • About 0.5 seconds more per million values of a datetime column, because each value becomes a PHP DateTimeImmutable.
  • About a second per million rows for a closure step, which converts the data to a DataFrame and back. Pipeline C runs its closure that way.

A pipeline that returns every row of a table with a datetime column can therefore be slower on PolarsTable than on DataFrame. In phibble’s harness, mutate() and left_join() returning 1M rows took 1.3 seconds on PolarsTable and 0.3 seconds on DataFrame.

PolarsTable suits pipelines that reduce the data before collecting (summaries, filters, distinct(), or a join followed by a summary), that chain several steps, or whose data starts in Polars: PolarsTable::fromPolars(Phpolars\read_csv($path)) skips phibble’s CSV parse. Expressions keep every step in Polars.
