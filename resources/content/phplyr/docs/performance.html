phplyr’s functions call one or two methods of the table they are given, so the backend determines how fast a pipeline runs. Benchmarks has the timings of phibble’s workloads and of three pipelines on each backend and in dplyr.

Choosing a backend

  • In-memory DataFrame suits data that fits in memory. Expression arguments, such as mean('x') and col('x')->gt(0), run faster than closures, because phibble computes expressions in one pass without building a table per group.
  • A database table (Phibble\tbl()) avoids loading the data into PHP. With expressions, filter() and summarise() run in the database, and only the result reaches PHP.
  • Pipelines that return every row (mutate(), arrange(), unfiltered joins) spend most of their database time transferring rows to PHP.
  • Closures on a database table load all rows first and then run in memory. Use col() expressions and phplyr’s helpers to keep the work in SQL.
  • SQLite columns need declared types. PDO binds values as strings. In an untyped column, SQLite stores them as text and compares numbers as text.
  • PolarsTable (phibble’s Polars backend, on the phpolars extension) runs expressions in Polars and converts the result to PHP values. Workloads that reduce the data gain the most. Workloads that return every row after little computation, such as a mutate() or a join, spend most of their time converting the result.
  • Closure steps on PolarsTable convert the data to a DataFrame and back, so closures run slower on PolarsTable than on DataFrame.
  • Data that starts in Polars can skip phibble’s CSV parse with PolarsTable::fromPolars(Phpolars\read_csv($path)).
