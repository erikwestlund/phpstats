phplyr’s functions call one or two methods of the table they are given, so the backend determines how fast a pipeline runs. These timings cover the workloads and machine below.

Methods

Every record comes from one Linux machine: two pinned AMD Zen 5 cores (Ryzen 9 9955HX), 8 GB of memory, Ubuntu 24.04, and PHP 8.5.12, with phibble 0.6.0 and phpolars 0.2.1 (Polars 0.55.2 at two threads). DataFrame and SQLite run single-threaded. Each timing is the median of seven runs, and each record lists every run.

The harness data comes from bench/generate.php, with phibble’s generator and seed. events.csv has 1,000,000 rows of id, key (10,000 values), g (8 labels), x (float, about 2% NA), and t (datetime). dims.csv has 100,000 rows of key, label, and w.

phplyr’s overhead

The median phplyr pipeline and the median direct table calls differed by at most 3%, with two exceptions. The 15 ms PolarsTable summary differed by 1.2 ms. The closure filters varied by up to 40% from run to run in both forms.

Choosing a backend

  • In-memory DataFrame suits data that fits in memory. In the grouped summary above, expression arguments took 0.15 s and closures 0.46 s, because phibble computes expressions in one pass without building a table per group.
  • A database table (Phibble\tbl()) avoids loading the data into PHP. With expressions, filter() and summarise() run in the database, and only the result reaches PHP.
  • Pipelines that return every row (mutate(), arrange(), unfiltered joins) spend most of their database time transferring rows to PHP.
  • Closures on a database table load all rows first and then run in memory. Use col() expressions and phplyr’s helpers to keep the work in SQL.
  • SQLite columns need declared types. PDO binds values as strings. In an untyped column, SQLite stores them as text and compares numbers as text.
  • PolarsTable (phibble’s Polars backend, on the phpolars extension) runs expressions in Polars and converts the result to PHP values. Every expression workload above was faster than on DataFrame except the mutate() and the join, which return all 1M rows after little computation.
  • Closure steps on PolarsTable convert the data to a DataFrame and back, so both closure workloads above were slower on PolarsTable than on DataFrame.
  • Data that starts in Polars can skip phibble’s CSV parse with PolarsTable::fromPolars(Phpolars\read_csv($path)).

Backend pipelines

bench/backends.php checks that every backend returns the same rows, and bench/backends.R checks dplyr’s row counts and column sums against phplyr’s.

  • A: filter, join a store lookup, two-key summarise, then a ranking window.
  • B: grouped lag(orderBy:), cumsum(), and a share of the group total over all rows.
  • C: pipeline A with a closure in filter(). It has no dplyr version, because its closure is PHP code.

The input is a generated sales table, with no date or datetime columns, joined to a 100-row stores table.
