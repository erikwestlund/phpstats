phplyr’s functions call one or two methods of the table they are given, so the backend determines how fast a pipeline runs. These timings cover the workloads and machines below.

Both benchmark sets ran on 2026-11-01 on an Apple M5 Ultra with PHP 8.5.10, phibble 0.6.0, and phpolars 0.2.1 (Polars 0.55.2, two threads). DataFrame and SQLite run single-threaded.

phplyr’s overhead

The phplyr pipeline and the same calls made directly on the table differed in both directions, by at most 13% at 1,000,000 rows. At 100,000 rows, the largest difference was 16 ms. Grouped slices, pivot_*(), and complete() build on the same table methods.

Choosing a backend

  • In-memory DataFrame suits data that fits in memory. In the grouped summary above, expression arguments took 0.17 s and closures 0.40 s, because phibble computes expressions in one pass without building a table per group.
  • A database table (Phibble\tbl()) avoids loading the data into PHP. With expressions, filter() and summarise() run in the database, and only the result reaches PHP. These timings exclude loading the data.
  • Pipelines that return every row (mutate(), arrange(), unfiltered joins) spend most of their database time transferring rows to PHP.
  • Closures on a database table load all rows first and then run in memory. Use col() expressions and phplyr’s helpers to keep the work in SQL.
  • SQLite columns need declared types. PDO binds values as strings. In an untyped column, SQLite stores them as text and compares numbers as text.
  • PolarsTable (phibble’s Polars backend, on the phpolars extension) runs expressions in Polars. A closure step converts the data to a DataFrame and back, so the closure workloads above were slower on PolarsTable than on DataFrame.

Backend pipelines

bench/backends.php times three phplyr pipelines and checks that DataFrame, PolarsTable, and SQLite return the same rows. It is adapted from phpolars’ benchmark script. bench/backends.R runs pipelines A and B with dplyr and checks that its row counts and column sums match phplyr’s.

  • A: filter, join a store lookup, two-key summarise, then a ranking window.
  • B: grouped lag(orderBy:), cumsum(), and a share of the group total over all rows.
  • C: pipeline A with a closure in filter(). It has no dplyr version, because its closure is PHP code.

The full results, with every repeat and version, are in benchmarks/backends-results.json and benchmarks/dplyr-results.json.

PolarsTable’s cost outside Polars is converting results to PHP values and running closure steps. Measured separately on the 1M-row events.csv, best of three:

  • Collecting four plain columns took 0.15 s, and the datetime column t added about 0.01 s.
  • A closure in filter() took 0.88 s, most of it converting the data to a DataFrame and back.

PolarsTable suits pipelines written in expressions, especially ones that reduce the data before collecting, and data that starts in Polars: PolarsTable::fromPolars(Phpolars\read_csv($path)) skips phibble’s CSV parse.
